How to use it

Running in two minutes

Start it on your PC

Install Node.js, then npm install and npm start. No account, nothing in the cloud.

Turn on telemetry

In F1 26: Settings → Telemetry → UDP On, port 20777, format 2025 or later.

Open it beside you

Scan the QR code it prints with a tablet or phone on the same Wi-Fi. Then drive; it talks when it matters.

How it works

From a packet to a call, in under a millisecond

Six steps, run ten times a second. Follow one call through them: the car behind closing in.

  1. F1 26 sends telemetry over your network, up to 60 times a second.

    Lap Data packet
    1,399 bytes · 24 car slots

  2. 16 binary packet types, read byte by byte. Corrupt ones are dropped.

    car 7 · P8
    gap ahead 612 ms

  3. Every car's laps, gaps and tyres, on game time. A flashback rewinds it.

    SAINZ 0.6 s behind
    closing 0.3 s / lap

  4. Measures pit loss, fits tyre wear, simulates every stop, scores the chance of a pass.

    pass chance 41%
    likely into turn 1

  5. Rules turn it into one call and a radio line. The most urgent one wins.

    DEFEND
    watch turn 1

  6. Sent to any browser on your Wi-Fi, 10 times a second, and read out loud.

    "Sainz 0.6 behind,
    defend turn 1."

Step 1 · The game

F1 26 broadcasts; the bridge listens

The game pushes binary UDP datagrams at a fixed rate. Nothing is requested and nothing is acknowledged: a lost packet is simply gone, so everything downstream has to cope with gaps.

Telemetry goes to UDP port 20777, at the send rate chosen in the game's settings (20, 30 or 60 Hz), as packet format 2025 or 2026. Each packet type has its own rate: positions and telemetry at the send rate, session data a couple of times a second, events only when something happens.

Why a bridge process? A browser can't open a raw UDP socket, and iOS restricts UDP listening for apps. So a small Node.js process beside the game takes the stream, does all the work, and serves the result to any browser on the network over a WebSocket. A phone or tablet only needs a browser, and the public demo can run the same dashboard from a file.

On a console or a second PC, the game is pointed at the bridge PC's LAN address; on the same PC it's localhost.

// src/udp/listener.js
socket.on('message', (msg) => {
  if (onRawPacket) onRawPacket(msg); // recording
  onPacket(parsePacket(msg));        // the pipeline
});
socket.bind(20777);

Code: udp/listener.js

Every packet starts with the same 29 little-endian bytes, unchanged from F1 23 to F1 26. Byte 6 says which of the 16 packet types follows. Three fields do most of the work downstream:

  • sessionUID: a new session resets the field model, so a qualifying lap never leaks into the race.
  • sessionTime: game time. Gaps and closing rates are measured on it, not on the PC's clock, and when it runs backwards a flashback happened.
  • overallFrameIdentifier: unlike frameIdentifier it never rewinds, so a jump in it is a lost packet. That's how feed loss is measured.

Code: udp/parsers/header.js

Lap Data is the spine: position, gap to the car ahead and to the leader, lap distance, pit status and penalties for every car. Because the game already sends the whole field, gaps, closing rates and undercut threats cost nothing extra to compute.

Offline, Car Telemetry and Car Damage also carry every car's speed, pedals and tyre wear, not just yours. That's what lets the tool trace a rival's best lap and time each AI car's next stop from its own wear.

Format 2026 has 24 car slots in every per-car array (22 before), confirmed by dividing real packet lengths by the old struct sizes.

The published spec is for F1 25. Every assumption was checked against recorded F1 26 races, and several were wrong:

  • A field inserted mid-struct. Car Status grew from 55 to 59 bytes with ersHarvestLimitPerLap placed before ersDeployedThisLap, not at the end. Found from a 6.2 MJ value at that offset on a stationary car.
  • Forecast times. The weather slots count minutes from now, not from the session start: 100% of 299 checks against 48%.
  • Fuel. fuelRemainingLaps is the MFD surplus over the race distance, not laps of fuel, worked out from the real burn rate.
  • Gap to leader reads 0 while a car is in the pit lane, so a naive rejoin model counted every car mid-stop as leading the race (8 places off).
  • Penalty types changed meaning. Type 16 ("Retired") arrived for a driver still racing; type 6 ("Disqualified") for one who then set the fastest lap. Neither reaches the radio.

Step 2 · Decode

Bytes into plain objects, defensively

One function reads every packet, live or recorded. It has to survive a game update changing a struct, a packet cut short, and garbage on the LAN.

parsePacket() reads the header, looks the packet id up in a table of 14 parsers, and returns { header, data }. Motion, lobby and time-trial packets aren't needed and return data: null.

The same function is fed by the live UDP socket, by the recorded-file replayer, by the capture analyzer, by the dataset builder and by the tests. That's why the public demo can't drift from the real tool: it is the real tool, fed from a file.

function parsePacket(buf) {
  const header = parseHeader(buf);
  const parse = PARSERS[header.packetId];
  if (!parse) return { header, data: null };
  // 24 slots from format 2026, 22 before
  return { header, data: parse(buf, carSlotsFor(header)) };
}

Code: udp/parsePacket.js

Per-car structs are packed back to back. Rather than trusting a hard-coded size, each parser works out the stride from the packet's length, reads the fields it knows, and jumps to the next car.

When F1 26 grew Car Status by 4 bytes, the parser kept reading its known prefix and picked the new field up by stride. A layout it can't explain logs one warning for that packet type, never garbage and never a crash.

Packet length alone can't give the number of car slots: F1 25's 1,320-byte telemetry array divides evenly by both 22 and 24. So the slot count comes from the header's packet format, and the stride from the length.

const carsBytes = buf.length - HEADER_LENGTH;
const stride = Math.floor(carsBytes / numCars);
if (carsBytes % numCars !== 0 || stride < 55) {
  console.warn(`[carStatus] packet size mismatch: ${buf.length} bytes`);
}
// F1 25: 55 bytes, F1 26: 59 bytes
ersHarvestLimitPerLap: stride >= 59 ? r.f32() : null,
r.offset = start + stride; // skip what we don't know

Code: parsers/carStatus.js

The bridge listens on the local network and trusts nothing it hears. A sequential little-endian reader throws a RangeError on a short read, and on any non-finite float: the game never sends NaN or Infinity (none in 2.26 million captured packets), so one means the packet is corrupt. The pipeline drops it and carries on.

A fuzz test sends seeded random, truncated and bit-flipped packets through the whole pipeline mid-race and checks that no exception escapes, every snapshot is valid JSON with finite numbers, and a clean session played afterwards gives the same result as without the fuzz.

It found a real bug before any user did: a NaN tyre-wear float stuck in the wear history, and the wear rate read "null" for the rest of the stint.

f32() {
  const v = this.buf.readFloatLE(this.offset);
  this.offset += 4;
  if (!Number.isFinite(v))
    throw new RangeError(`non-finite float at byte ${this.offset - 4}`);
  return v;
}

Step 3 · Track the field

One model of every car, on game time

The field model files each packet under its car and keeps the history the analysis needs. It holds facts only; no opinions, no calls.

For each of the 22-24 cars, the latest of every packet, plus:

  • Lap history, the last 12 laps: time, tyre compound and age, fuel, and two flags - did the lap touch the pit lane, did any of it run under a safety car. Those flags are exactly what's needed to measure what a pit stop costs and to keep slow laps out of pace figures.
  • Gap samples to the car ahead, once a second of game time, two minutes deep: the closing rate per lap.
  • Battery at each crossing of the line, and in 20 slices of the last lap: how this car spends its energy, lap after lap.
  • 25 mini-sectors per lap, timed from lap distance: where a car is quicker, and what damage costs.
  • Lap traces: speed, throttle and brake against distance, for the debrief's lap comparison.

Code: state/fieldModel.js · state/lapTrace.js

There are two clocks, and they're kept apart. Game time (the header's sessionTime) measures the race: gap samples are taken every second of it, so a closing rate means the same at 20 Hz or 60 Hz, and pausing the game doesn't skew it.

The engine's clock (card expiries, settle timers) is injected into the pipeline rather than read from Date.now(). Live it's the wall clock; in a replay it's the recording's own clock. So a replay at 8× gives exactly the same calls as one at 1×, and that's a test.

// one pipeline, any clock
const pipeline = createPipeline({
  now: () => replayClockMs,   // or Date.now live
});
pipeline.feed(buf);   // every packet
pipeline.tick();      // every 100 ms -> snapshot

Code: pipeline.js · test: two replays at different speeds give identical calls

A flashback rewinds the race a few seconds. If the model just kept appending, it would record laps that never happened: one real Monaco race with 20 flashbacks produced laps 3, 4, 3, 4... and polluted the pace, tyre-wear and pit-loss figures.

Two signals give it away: sessionTime runs backwards, or the lap counter drops. Either way, everything recorded after that point is removed: laps, battery history, mini-sectors, passes. The lap rewound into keeps the flags it already had.

The datasets do the same: a lap taken back by a flashback is taken back from laps.csv, and so are the calls made on it.

if (header.sessionTime < sessionTime - 0.5) {
  // game time went backwards: undo later passes
}
if (c.currentLapNum < prevLapNum) {
  car.lapHistory = car.lapHistory.filter(
    (l) => l.lapNum < c.currentLapNum);
  car.ersHistory = car.ersHistory.filter(...);
  car.miniSectors = car.miniSectors.filter(...);
}

Code: state/fieldModel.js

Track memory. What a race measured at a track - the pit loss, the tyre age share and wear the AI boxed at, each compound's wear rate from practice - goes into a small JSON file. The next race there starts from those numbers instead of a generic guess. Replays and tests use no memory, so they stay reproducible.

Feed health. Car Telemetry's frame counter steps by 1 between packets at 60 Hz and by 3 at 20 Hz. A step of twice the usual is one packet lost, and a pause isn't. Loss over the last 10 seconds shows on the link chip ("Live · 8% lost") from 2%, and nothing extra when the feed is fine.

Step 4 · Analyse

The numbers a strategist would work out

Every 100 ms the engine runs a set of pure functions over the field. Each is scored on real races against the guess it has to beat.

Clean pace is the mean of a car's last 3 clean laps: not a pit lap, not under a safety car, not lap 1, and not more than 7% slower than its own typical lap (a spin or traffic).

Pit loss is measured, not assumed. Whenever any car makes a green-flag stop, its in-lap plus out-lap minus two clean laps is what the stop cost. Readings between 8 and 45 s are kept, and the median is used. Before any stop, it falls back to earlier races at this track, then a per-track estimate, then 22 s. Under a safety car a stop costs about 55% of that, under a VSC 65%.

Rejoin: add the pit loss to your time behind the leader and see where that slots in. Scored on 24 real stops it's 2.5 places off against 4.3 for "you keep your place" - but nearly all of the 2.5 is one direction, too pessimistic, and that's the next thing to fix.

loss = inLap.lapMs + outLap.lapMs
     - 2 * avg(cleanLaps.slice(-3))
if (loss >= 8000 && loss <= 45000) samples.push(loss)
pitLossMs = median(samples)       // measured
         ?? median(trackMemory)  // earlier races
         ?? TRACK_ESTIMATE ?? 22000
if (safetyCar) pitLossMs *= 0.55  // VSC 0.65

Code: engine/raceAnalysis.js

Tyre wear is learned live from the whole field, 22 cars' laps rather than just yours, so the estimate firms up within a few laps instead of waiting for your own stint.

Each car is compared only with itself (its laps minus its own average), so fast and slow cars share one wear slope per compound. Fuel and tyre age both rise one per lap until someone stops, so lap times alone can't separate them: the fuel effect is fixed from physics, the measured burn per lap × ~0.03 s per kg. Laps far off a car's own trend are trimmed with a robust (MAD) filter.

Each wear rate carries a 90% range from a bootstrap that resamples cars, not laps - cars are the independent units. On synthetic fields the range holds the true rate about 90% of the time. The fit runs once per completed lap (~10 ms), not every tick.

lapTime = carBase + deg × tyreAge
        - fuelEffect × lapNumber + noise

Code: ml/tyreModel.js · scored in CI on datasets/laps.csv

Pit timing races every possible stop lap, from now to the flag, lap by lap, against the cars around you. Your laps slow by the fitted wear rate per lap of tyre age; a fresh set starts quicker by the game's own estimate. Rivals keep their clean pace and stop when they're expected to, so a car about to box no longer counts as one you'd rejoin behind for good. Places lost at the rejoin carry a track-position cost: a faster car still has to get past. Under 1,000 small sums a lap.

When rivals stop: the AI's stop is a strategy, not a wear limit - at Monaco every car on mediums boxed at 12 laps on sets rated for 19-20. So each car is expected at a share of its set's rated life (60% as a prior), or by its own wear rate once the race has shown the wear the AI boxes at.

The race plan before the start: one stop or two, on which tyres. Each plan's total time is linear in the wear rates, so the search runs once (5,800 plans pruned to 500 shapes) and then 1,000 races with the wear rates and pit loss drawn as widely as they're uncertain take a few milliseconds. The card says "wins 87% of 1,000 simulated races".

// one simulated race
for each plan:
  total = Σ stints (setPace × laps
                   + deg[compound] × Σ tyreAge)
        + stops × pitLoss
// deg ~ its 90% range, pitLoss ~ its spread
winner = argmin(total)
odds   = wins / 1000

Code: pitTiming.js · racePlan.js · rivalStops.js

Will the car behind pass in the next 10 s? A logistic regression written from scratch - standardised features, an L2 penalty, class-weighted gradient descent - over the gap (log scale), the closing rate, the clean-pace difference, tyre age and compound, the battery difference and 2026 Overtake mode. It's trained on recorded races, labelled from the game's own overtake events, and scored on races it never saw. Held-out AUC 0.851 against 0.854 for the gap alone: it ties, so the app marks it experimental.

Battery at the line: drivers spend on the same straights every lap, so the rest of this lap is copied from the same stretch of the last one. 7.7 points off against 13.2 for "it stays where it is".

Where they'll attack: your braking zones, scored by where passes actually happen at this track, with the places you've been passed this session weighted twice.

p(pass) = σ(w · [log gap, closing, Δpace,
                 Δtyre age, compound,
                 Δbattery, overtakeMode] + b)

battery@line = now + (lastLap@line - lastLap@here)

Code: ml/logistic.js · batteryProjection.js · attackForecast.js

What damage costs is measured from your own mini-sectors: clean laps since the hit against clean laps before it, slice by slice, less what fuel burn and tyre wear alone would have changed. The slices say where the time goes (a front wing loses it in corners). Before a full lap has passed, the slices already run give an early figure, scaled up. A slice over three times its clean time is a crawl back to the pits, not pace, and is left out.

Weather: the forecast slots become "rain in ~4 laps". Once it's wet or drying, the crossover is read from the field: are the cars already on the other tyre lapping faster? The game sends no track-wetness figure, so the field's lap times are the evidence.

loss/lap = Σ_k (median(damaged[k]) - median(clean[k]))
         - drift(fuel, tyres)
worth a stop if  loss/lap × lapsLeft
               > pitLoss + noseChange

Step 5 · Decide

From numbers to one call and a radio line

The decision layer turns the analysis into what the driver hears - and it has to be calm about it: a call that flaps is worse than no call.

One call is always on screen: PUSH, HOLD, BOX or PIT (and PREP in qualifying). It's a pure function of the numbers the radio cards use, so the two can never disagree. The first rule that applies wins, in this order:

  1. In the pit lane → PIT
  2. A penalty to serve (not under a safety car) → BOX
  3. The wrong tyre for the weather → BOX
  4. Damage worth a stop → BOX
  5. A cheap stop under a safety car or VSC → BOX
  6. Tyres at the cliff → BOX (or HOLD if 2 laps are left)
  7. The pit window: this lap, by a clear margin → BOX
  8. Red flag, safety car or VSC → HOLD
  9. Fuel short, tyres near the cliff, fuel tight → HOLD
  10. An undercut on, rain coming, or all fine → PUSH

Each call carries a kind (why it was made), and the calm kinds - push, manage tyres, an undercut on offer - have to hold 5 s before they replace each other. BOX, PIT and a safety car come at once.

{ action: 'BOX', kind: 'cheap-stop',
  reason: 'Safety car: a stop costs ~11s, not ~21s' }
undercut flips 7 → 2 after the settle

Code: engine/calls.js

Everything else is a radio card with an id, a severity (info, advisory, critical), a category and an expiry. The rules that keep them calm:

  • Settled: who-and-where calls ("Defend from HADJAR") must hold for 5 s before they're said - in a train of cars the car ahead changes every few seconds.
  • Held text: when only the numbers change ("0.4s" → "0.3s"), the text holds for 5 s. Radio text must not tick.
  • One voice per topic: the battle call takes over the defend card instead of adding a second one.
  • Critical is rare: only what the driver can't see from the cockpit (a safety car, a red flag) interrupts the screen.
  • Only penalties whose meaning is certain reach the radio.
upsert('under-attack', {
  severity: 'advisory',
  category: 'pace',
  message: 'Defend from HADJAR - watch into corner 11',
  expiresAtMs: now + 4000,
})

With auto-switch on, the screen follows the race. It's decided on the server, not in the browser, so every device agrees and a replay always switches the same way.

Code: engine/focus.js

After the race, every call is graded by the one thing it claims, against the laps that followed:

  • PUSH claims the tyres hold: wrong if two green laps in a row fall 1.5 s off the pace before.
  • HOLD, manage tyres claims the cliff is near: right if a lap falls off within 3 laps.
  • BOX for damage claims the loss to the flag beats a stop.
  • BOX under a safety car claims the stop is cheaper than one under green - measured against the cars that didn't stop on those laps.

Following the rules (a penalty, the pit lane) isn't graded.

Step 6 · Your screen

One snapshot, ten times a second

Everything the dashboard shows travels in one JSON object. The browser formats it and reads the calls aloud; it never decides anything.

buildSnapshot() flattens the field, the analysis and the calls into one object: the entire contract between the bridge and the browser. It's pushed over a WebSocket at a fixed 10 Hz, whatever rate the game sends, which caps CPU on the PC and battery on the tablet. The bigger debrief rides along on every 10th tick, once a second.

A contract test records every field each widget reads and checks it exists in a real snapshot. A renamed field used to blank a card silently; now 5 of 5 planted renames fail a test.

Decode defensively

Each parser takes the per-car struct size from the packet's length, not a constant: F1 26 inserted fields mid-struct, and a layout change costs one warning, not a crash. A non-finite float marks the packet corrupt. Random, truncated and bit-flipped packets are fuzzed through the whole pipeline in the tests.

Model the field on game time

Every car is kept: its last packets, 12 laps of history with pit and safety-car laps flagged, gaps sampled once a second of game time - so a closing rate means the same at 20 Hz or 60 Hz, and a pause doesn't skew it.

Record everything, replay exactly

A capture saves every packet with its arrival time (.f1log.gz, ~300 MB a race). Replays run the same pipeline on the recording's clock, so a bug seen on Saturday can be reproduced, fixed and tested on Sunday, call for call.

Datasets from the raw stream

Captures stay local; small datasets built from them are committed: one row per race, per car per lap (1,631 laps), and every call made. CI scores the models on them.

Architecture

Five layers, wired once

Each layer only reads from the one above it. The live bridge, the replayer, the capture analyzer, the dataset builder and every test run the same createPipeline(), so none of them can drift from what the driver sees.

1udp/Ingest: the socket and one parser per packet id. Bytes in, plain objects out.
2state/The field: every car, updated packet by packet, rewound by flashbacks. Facts only.
3analysis/ · ml/Numbers: pure functions for pit timing, the race plan, rival stops, damage cost, tyre wear, overtake odds.
4engine/Decisions: runs the analysis every 100 ms and turns it into the call (PUSH / HOLD / BOX) and radio cards that settle before they're said.
5server/Out: one JSON snapshot, pushed over a WebSocket at a fixed 10 Hz. The browser formats; it never decides.

Case study

One race, six fixes

Barcelona, 23 laps, recorded on 17 October. The capture was replayed through the engine, every call graded against the laps that followed, and each problem became a failing test before it became a fix.

  • The call flickered

    "Undercut on" and "Tyres and fuel OK" swapped 7 times in 3.5 minutes as the gap hovered at the threshold.

    Fix

    A calm call has to hold 5 s before it replaces another. BOX, PIT and a safety car still come at once.

    7 → 2 calls

  • An undercut from P8 "rejoins P21"

    The rule checked for clean air but never whether you'd come out ahead of the car you were undercutting.

    Fix

    Only when fresh tyres gain more before they stop than the gap to them; it says by how much.

    gain > gap

  • ERS advice every 10-20 s

    The 2026 battery swings 20%+ inside a lap, so "Boost" and "battery low, save it" took turns.

    Fix

    Judged on the battery at the line, not the swing within the lap.

    74 → 46 a race

  • "You gain 5.46 s" into turn 1

    The pit lane runs over that stretch, and a pit lap was in the averaged mini-sectors.

    Fix

    Pit and safety-car laps left out; the median, not the mean.

    5.46 s → 0

  • Two defend calls taking turns

    The battle call and the older "right behind you" card spoke separately: 45 of 55 key radio calls.

    Fix

    One defend card; the battle call speaks on it.

    1.4 → 1.2 /min

  • "Disqualified" in qualifying

    The game sent penalty type 6 to a driver who went on to set the fastest lap - its meaning changed in F1 26.

    Fix

    Kept off the radio, like type 16 before it. Only penalties whose meaning is certain are said.

    off the radio
How it's built

Tests that find bugs, not tests that agree with the code

Test first, from the intended behaviour

Over 250 tests. Each new rule's test is written from what it should do and seen to fail before the code exists; assertions are never edited to pass. Known weaknesses stay in the suite as todo tests.

Mutation-checked

A test only counts once it fails on a planted bug. In the fixes above, 9 of 13 planted bugs were caught at first; each survivor got a test, and all 13 are caught now.

Gates in CI

Coverage can't drop below 88% of lines; the model backtests can't get worse; a tick-time budget and a contract test that tracks every snapshot field a widget reads.

Real packets, real races

Parsers are pinned on packets captured from F1 26; scenario tests replay a scripted race and check each call follows its cause - and never comes before it.
